# Ревью и закрытие задачи

Фаза начинается, когда все шаги плана `[x]` или `[!]`.

## 1. Самопроверка диффа

Просмотри весь дифф задачи: `git diff <база>...HEAD` и `git diff --stat <база>...HEAD`. Затем прогони механическую проверку всех коммитов задачи — она находит то, что глаз пропускает:

```bash
bash <SKILL>/scripts/check-commit.sh --range <база>..HEAD
```

Нет bash — пройди пункты «Тесты» и «Подавления» вручную и напиши в отчёте, что скрипт не запускался. Заморозка контрольными суммами — дополнительно `bash <SKILL>/scripts/freeze.sh verify <список> HEAD` по каждому списку задачи: отпечаток списка должен совпасть с записанным в журнале при заморозке, а перезаморозки — с согласованными правками.

Чек-лист:

- [ ] **Рамки.** Изменены только файлы, нужные для требований. Посторонний рефакторинг и «заодно поправил» — убрать; идеи — в отчёт как предложения.
- [ ] **Тесты.** Существующие тесты и снапшоты меняются только в коммитах `test(...)`; каждое изменение после заморозки согласовано. Проверка: `git log --format='%h %s' --name-status <база>..HEAD -- <пути тестов>`.
- [ ] **Подавления и пропуски.** Нет новых `skip`/`xfail`/`.only`/`noqa`/`type: ignore`/`eslint-disable`/`@ts-ignore`/`nolint` и т. п. (`check-commit.sh` выше).
- [ ] **Отложенное.** Нет коммитов `wip:` в истории задачи, забытых веток `parked/<slug>/…` (`git branch --list 'parked/*'`) и неприменённых патчей `parked-step-*.patch` в папке задачи.
- [ ] **Мусор.** Нет отладочного вывода, закомментированного кода, временных файлов, `TODO` без пояснения.
- [ ] **Хардкод.** Нет значений, подогнанных под тестовые данные; конфигурация вынесена туда, где её ищут в этом проекте.
- [ ] **Ошибки.** Нет проглоченных исключений; сообщения об ошибках понятны; ошибочные пути покрыты тестами.
- [ ] **Секреты.** Нет ключей, токенов, паролей, внутренних адресов.
- [ ] **Стиль.** Имена, структура и язык комментариев соответствуют проекту.

Найденное исправь (на зелёных тестах) или запиши в «Известные ограничения» с объяснением.

## 2. Документация

Если изменилось поведение, публичный API, конфигурация или способ запуска — обнови то, что в проекте уже есть: README, CHANGELOG, документацию API, `.env.example`, примеры. Не создавай новых документов без необходимости.

## 3. Финальный прогон

Полный набор тестов, линтер, типы, сборка — командами из `.ai/PROJECT.md`. Сверь с Baseline построчно: что было, что стало, новых падений нет. Вывод — в финальный отчёт.

## 4. Независимое ревью

Автор не должен проверять сам себя, поэтому ревьюер — отдельный агент или отдельная сессия без контекста разработки:
- **L — обязательно**, перед слиянием в основную ветку;
- **M — рекомендуется**, если меняется публичный API, безопасность, данные или задача шла в автономном режиме.

Ревьюеру передаётся только: спецификация (`SPEC.md` или раздел `TASK.md`), дифф задачи, команды проверок, путь к skill (для скриптов). Задание ревьюеру:

```
Проверь дифф против спецификации. Не правь код. Верни список находок с уровнем (блокер / важно / мелочь):
1. Какие REQ не реализованы или реализованы не так, как написано.
2. Поведение сверх спецификации.
3. Признаки подгонки тестов: правки существующих тестов вне коммитов test, хардкод, моки тестируемой логики,
   подавления, пропуски. Запусти: bash <SKILL>/scripts/check-commit.sh --range <база>..<ветка>
   (и freeze.sh verify <список> <коммит>, если заморозка контрольными суммами).
4. Ошибки обработки ошибок, граничных случаев, безопасности.
5. Запусти проверки из спецификации и приложи сводку вывода.
```

В Claude Code ревьюер — субагент; в других агентах — новая сессия с теми же входами. Если запустить отдельного агента или сессию сам не можешь (нет субагентов), не проверяй себя вместо ревьюера: отдай пользователю готовое задание выше с путями и командами, чтобы он запустил его в новой сессии, а в отчёте напиши «Независимое ревью: не проводилось — нужен запуск, задание передано». Для L слияние ждёт результата ревью.

Находки уровня «блокер» исправляются до приёмки; остальные — исправляются или попадают в «Известные ограничения» с согласия пользователя.

## 5. Финальный отчёт и приёмка

Выдай финальный отчёт (`references/reporting.md`).
- Интерактивный режим — дождись приёмки.
- Автономный режим — отчёт и остановка. Не сливай и не пушь без разрешения, данного заранее.

## 6. Закрытие (после приёмки)

1. Слияние, push, PR — только по решению пользователя (`references/git-safety.md`).
2. **Архивация — до удаления worktree.** Сожми файлы-якоря в `$MAIN/.ai/archive/<ГГГГ-ММ-ДД>-<slug>.md` — цель, требования, ключевые решения, допущения, коммиты, известные ограничения (до ~40 строк). Затем удали папку `$MAIN/.ai/tasks/<slug>/` и файл `$MAIN/.ai/ACTIVE` — это собственные артефакты задачи. `$MAIN` — основная рабочая копия (SKILL.md, п. 8): архив в worktree пропал бы вместе с ним.
3. Удали собственные worktree (`git worktree remove <путь>`, без `--force`; отказ означает незакоммиченные правки — остановись и разберись) и свои временные ветки: слитые `wip/<slug>/…` и `integration/<slug>` (`git branch -d`), отработанные `parked/<slug>/…` (`git branch -D`). Удалённые (remote) ветки — только с согласия.
4. Дополни `.ai/PROJECT.md` тем, что стоит знать следующим задачам: новые команды, нестабильные тесты, особенности окружения.
5. Ретроспектива (для L обязательно, для M — если было что сказать): 1–3 строки в архив о том, какие правила регламента мешали, не сработали или чего не хватило. Если вывод касается самого регламента — предложи пользователю правку skill.
