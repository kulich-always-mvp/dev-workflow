# Discovery: изучение проекта, Baseline, вопросы

Цель фазы — понять проект и задачу настолько, чтобы спецификация не содержала двусмысленностей, и зафиксировать исходное состояние, с которым потом сверяется результат.

## 1. Профиль проекта `.ai/PROJECT.md`

Папка `.ai/` всегда лежит в основной рабочей копии (SKILL.md, п. 8). Найти её из любого worktree:

```bash
MAIN=$(git worktree list --porcelain | sed -n '1s/^worktree //p')   # дальше: "$MAIN/.ai/"
```

1. Если файл есть — прочитай его и опирайся на него. Проверь, что команды в нём ещё актуальны (файлы, на которые он ссылается, существуют).
2. Если файла нет — собери сведения из кода, не спрашивая пользователя:
   - манифесты и скрипты: `package.json`, `pyproject.toml`, `Makefile`, `go.mod`, `Cargo.toml`, `build.gradle`, `*.csproj` и т. п.;
   - конфигурация CI (`.github/workflows/`, `.gitlab-ci.yml`) — там обычно точные команды проверок;
   - `README`, `CONTRIBUTING`, `AGENTS.md`, `CLAUDE.md`;
   - стиль коммитов (`git log --oneline -20`) и язык комментариев;
   - **хуки проекта:** `.husky/`, `.pre-commit-config.yaml`, `lefthook.yml`, `git config core.hooksPath`, файлы без `.sample` в `.git/hooks/`. Главное — запускают ли они тесты при коммите: тогда красный коммит заморозки невозможен, и нужна заморозка контрольными суммами (`references/tdd.md`, «Заморозка»).
3. Заполни `templates/PROJECT.md` и сохрани в `$MAIN/.ai/PROJECT.md`. Скрой `.ai/` от git локально, не меняя файлов репозитория (если в профиле не решено иначе):

   ```bash
   grep -qxF '.ai/' "$(git rev-parse --git-path info/exclude)" 2>/dev/null || printf '.ai/\n' >> "$(git rev-parse --git-path info/exclude)"
   ```

   Покажи профиль пользователю (мягкий гейт): «Профиль проекта составлен, проверьте команды, политику git, коммиты агентом и способ заморозки». Для M — в том же сообщении, что и вопросы гейта ТЗ (п. 4–6), чтобы не гонять пользователя дважды; для L — отдельным сообщением до вопросов. Неизвестное пометь `[?]`, а не выдумывай.
4. По ходу работы дополняй профиль новыми фактами (команда, нестабильный тест, особенность окружения).

## 2. Состояние репозитория

Перед любыми правками:

```bash
git status --porcelain
git branch --show-current
git stash list
```

- **Чистое дерево** — создай ветку задачи (`references/git-safety.md`, «Ветки»).
- **Текущая ветка не основная и не защищённая** — скорее всего, это рабочая ветка пользователя. По умолчанию ветка задачи создаётся от неё (база = текущая ветка); в интерактивном режиме уточни одним вопросом.
- **Есть незакоммиченные изменения пользователя:**
  - интерактивный режим — спроси: закоммитить их, отложить в stash или работать поверх (по умолчанию: работать поверх, не трогая эти файлы). Если пользователь выбрал stash: `git stash push -u -m "user: до задачи <slug>"`, в журнал — SHA (`git rev-parse stash@{0}`);
  - автономный режим — создай отдельный worktree от `HEAD` (`git worktree add ../<repo>-<slug> -b <ветка>`) и работай там. Запись рядом с папкой проекта может требовать подтверждения среды; если его не получить, используй встроенную изоляцию среды (в Claude Code — worktree самой сессии или субагента), а если и её нет — остановись с отчётом. Рабочую копию пользователя не трогай; файлы-якоря при этом ведутся в `$MAIN/.ai/`.
- **Пустой репозиторий** (нет коммитов) — первый коммит с каркасом допустим в основной ветке после гейта плана (`references/git-safety.md`).
- **Нет git** — сообщи; предложи `git init` в плане. Работа без контроля версий допускается только с согласия.

Когда создаёшь папку задачи M/L (`$MAIN/.ai/tasks/<slug>/`), запиши `$MAIN/.ai/ACTIVE`: `<slug> · <ветка> · <путь к worktree или «основная копия»>` (SKILL.md, п. 8).

## 3. Baseline

Перед первым прогоном посмотри, что запускают тесты: маркеры `integration`/`e2e`, `.env`, строки подключения и адреса в конфигурации тестов. Тесты, которые ходят в боевые сервисы или реальные БД, без согласия не запускай (инвариант 4) — начни с модульных.

Запусти проверки из профиля проекта в неинтерактивном режиме и с таймаутами (`references/git-safety.md`, «Запуск команд»):

1. тесты (полный набор, если укладывается в таймаут);
2. линтер, проверка типов, сборка — что есть в проекте.

Установка зависимостей по существующему lock-файлу (`npm ci`, `pip install -r requirements.txt` в виртуальном окружении) — не новая зависимость и не гейт.

Запиши в журнал задачи сводку, а не лог:

```
Baseline (<дата>, коммит <short-sha>):
- тесты: <команда> → 412 passed, 3 failed, 5 skipped; падают: test_a, test_b, test_c
- линтер: <команда> → 12 ошибок (до задачи)
- типы: <команда> → 0 ошибок
- сборка: <команда> → ок
```

Особые случаи:
- **Падающие тесты** записываются как исходное состояние. Ты не обязан их чинить вне рамок задачи, но не имеешь права допустить новых падений и не имеешь права «чинить» их подгонкой.
- **Нестабильные тесты.** Падающий тест перезапусти один раз. Прошёл — это flaky: запиши в журнал и в `PROJECT.md`, не считай регрессией.
- **Baseline не запускается** (нужна БД, сервис, секрет, сеть): запиши причину и запусти то, что возможно. Явно пометь частичный прогон как частичный. Это блокер окружения — сообщи сразу.
- **Набор не укладывается в таймаут:** прогони релевантную часть, запиши, какая часть не прогнана, и предложи пользователю способ полного прогона (CI, ночной запуск).
- **Тестов в проекте нет:** первым шагом плана ставится «поднять тестовую инфраструктуру» (выбор фреймворка — это новая зависимость, жёсткий гейт).

## 4. Вопросы

Не задавай вопросов, ответ на которые есть в коде, профиле или стандартах проекта.

Пройди чек-лист. Каждый пункт либо выводится из кода, либо становится вопросом, либо становится допущением:
- цель и критерий успеха с точки зрения пользователя;
- входные и выходные данные: формат, объём, кодировки, граничные значения;
- ошибки: что считается ошибкой, как сообщать, нужен ли повтор или восстановление;
- окружение: ОС, язык и версия, фреймворк, менеджер пакетов, ограничения по зависимостям;
- нефункциональные требования: производительность, безопасность, логирование, локализация;
- что **вне рамок** задачи (non-goals);
- для bugfix: шаги воспроизведения, ожидаемое и фактическое поведение;
- для refactor: что гарантированно не должно измениться.

Формат: один пакет, по приоритету. Лимит: S — 0 (кроме неоднозначности), M — до 5, L — до 10. Каждый вопрос — с вариантом по умолчанию и одной строкой обоснования:

```
1. Как обрабатывать пустые строки в CSV? — По умолчанию: пропускать и считать в отчёте, т. к. текущий импорт XLSX делает так же.
```

Если вопросов нет — так и скажи.

## 5. Допущения

Всё, что решено без явного ответа пользователя, записывается в раздел «Допущения» спецификации и показывается пользователю:

```
[ДОПУЩЕНИЕ A-1] Пустые строки пропускаются. Почему: так работает импорт XLSX (src/import/xlsx.py:88). Как отменить: REQ-4 → «ошибка на пустой строке».
```

Молчаливых допущений быть не должно.

## 6. Итог фазы

Сформируй ТЗ (раздел спецификации в `TASK.md` для M или `SPEC.md` для L): требования `REQ-n` с проверяемыми формулировками, non-goals, допущения, глоссарий при необходимости. Пройди гейт ТЗ (SKILL.md, п. 5). В интерактивном режиме без подтверждения («да», «ок», «подтверждаю») к планированию не переходи.
