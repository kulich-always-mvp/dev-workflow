# Оркестрация нескольких агентов (класс L)

Схема: ведущий агент (оркестратор) делит работу на независимые части, раздаёт их агентам-исполнителям (воркерам), каждый работает в своей изолированной копии репозитория (git worktree), затем оркестратор проверяет и сливает результаты по одному.

## 1. Когда распараллеливать

Распараллеливай, только если **все** условия выполнены:
- есть минимум 2 подзадачи, каждая размером не меньше M;
- подзадачи почти не пересекаются по файлам;
- контракты между ними (интерфейсы, типы, API) можно зафиксировать заранее;
- выигрыш во времени оправдывает расход: каждый воркер заново читает контекст и тратит токены.

Не распараллеливай, если подзадачи сильно связаны, если контракт ещё не ясен (сначала spike или последовательная реализация ядра), если суммарный объём невелик. В этих случаях L-задача выполняется последовательно одним агентом по обычному маршруту.

## 2. Роли

| Роль | Делает | Не делает |
|---|---|---|
| Оркестратор | фаза 0, декомпозиция, контракты, проверка результатов, интеграция, ведение `PLAN.md`/`PROGRESS.md`, общение с пользователем | не принимает отчёт воркера на слово |
| Воркер | реализация в рамках контракта в своём worktree, отчёт | не правит замороженные тесты, файлы фазы 0, `PLAN.md`, `PROGRESS.md`; не выходит за контракт |
| Ревьюер | независимое ревью итогового диффа (`references/review-and-close.md`, п. 4) | не правит код |

## 3. Фаза 0: контракт до работы

Оркестратор сам, до запуска воркеров:
1. Создаёт ветку интеграции `integration/<slug>` от базовой.
2. Коммитит общие интерфейсы, типы, контракты API, схемы данных, каркасы с заглушками.
3. Коммитит зависимости (после жёсткого гейта по каждой новой).
4. **Пишет красные тесты для каждой подзадачи** и коммитит их (`test(...)`) — это заморозка. Воркеры получают готовые тесты и не могут их менять.

*Почему: если воркер сам пишет и тесты, и код, проверка перестаёт быть независимой. Тесты от оркестратора делают подгонку у воркера бессмысленной.*

**Если хуки проекта запускают тесты при коммите**, красный коммит фазы 0 невозможен без обхода хуков, а обход — жёсткий гейт (инвариант 4). Подготовь коммит (файлы в индексе, готовое сообщение) и попроси пользователя выполнить его самому в своём терминале. Контрольные суммы здесь не подходят: воркерам нужны тесты в истории, иначе их worktree их не увидят.

## 4. Контракт воркера

Каждому воркеру выдаётся контракт по шаблону `templates/worker-contract.md`: цель и **полный текст** нужных `REQ-n`; файлы, которые можно менять; запрещённые файлы; тесты, которые должны стать зелёными; команды проверок; ресурсы окружения (порт, БД, временный каталог); DoD; формат отчёта (`templates/worker-report.md`).

Контракт самодостаточен: папка `.ai/` лежит в основной рабочей копии и в worktree воркера не попадает (SKILL.md, п. 8). Если воркеру нужна вся спецификация — дай абсолютный путь к `SPEC.md` только для чтения.

Воркер может добавлять новые тесты в своей области. Если для выполнения нужно выйти за контракт (тронуть чужой файл, изменить интерфейс, поменять тест) — воркер останавливается и сообщает оркестратору, а не решает сам. Незавершённое воркер коммитит в свою ветку (`wip: …`), а не в stash; если хуки проекта не пропускают красный коммит — сохраняет патч по `references/git-safety.md`, п. 3, и указывает его путь в отчёте.

В Claude Code `guard-edit.sh` в worktree воркера защищает тесты фазы 0: они уже в `HEAD` ветки воркера, поэтому их правку сторож не пропустит, а дописывание новых тестов — пропустит.

## 5. Изоляция

- Каждый воркер — свой worktree и своя ветка `wip/<slug>/<n>` от `integration/<slug>`.
- Зависимости устанавливаются в каждом worktree отдельно.
- Общие ресурсы разводятся: порт = базовый + n, отдельная БД или схема с суффиксом `_<n>`, свой временный каталог. Конкретные значения — в контракте.
- Основная ветка и ветка интеграции воркерами не меняются.

В Claude Code: субагенты с изоляцией в worktree. В Codex и других агентах: отдельные сессии, каждая запущена в своём worktree.

## 6. Проверка результата воркера

Оркестратор по каждому отчёту:
1. Сам запускает тесты и проверки в worktree воркера; сравнивает с отчётом.
2. Проверяет дифф `git diff integration/<slug>...wip/<slug>/<n>`:
   - изменены только разрешённые файлы;
   - замороженные тесты и файлы фазы 0 не тронуты (`git diff --stat integration/<slug>...wip/<slug>/<n> -- <пути>` пуст);
   - нет нарушений инварианта 2: `bash <SKILL>/scripts/check-commit.sh --range integration/<slug>..wip/<slug>/<n>`. Коммиты `wip:` воркера здесь ожидаемы: перед слиянием попроси воркера переоформить их в обычные коммиты или слей ветку через `git merge --squash` с понятным сообщением.
3. Принимает или возвращает с конкретными замечаниями.

Повторный провал по тому же контракту — сузь подзадачу, разбей её или выполни сам. Не перезапускай воркера с тем же контрактом в третий раз.

## 7. Интеграция

1. Ветки воркеров сливаются в `integration/<slug>` **по одной** (`git merge --no-ff`).
2. После каждого слияния — полный прогон тестов, линтера, типов, сборки; затем оркестратор обновляет `PLAN.md` и `PROGRESS.md`.
3. Конфликты разрешает оркестратор по спецификации; при неоднозначности — вопрос пользователю.
4. После всех слияний — независимое ревью (обязательно для L).
5. В основную ветку — только после зелёного полного прогона и подтверждения пользователя.
6. Уборка — `references/review-and-close.md`, п. 6.
