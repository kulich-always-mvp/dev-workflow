# TDD-контракт: шаг реализации

Порядок для каждого шага плана:

```
каркас → тесты → красный статус (правильная причина; для refactor — контрольная поломка) → заморозка →
реализация → тесты шага → полный набор + сверка с Baseline → рефакторинг → линтер/типы/сборка → коммит → якоря
```

## 1. Каркас интерфейса

До тестов разрешено создать публичные сигнатуры (функции, классы, типы, маршруты) с телом-заглушкой:

| Язык | Заглушка |
|---|---|
| Python | `raise NotImplementedError` |
| JS/TS | `throw new Error("not implemented")` |
| Go | `panic("not implemented")` |
| Rust | `todo!()` |
| Java/Kotlin/C# | `throw new UnsupportedOperationException()` / `TODO()` / `throw new NotImplementedException()` |

Это не функциональный код. *Почему: без каркаса тест упадёт на импорте, а это неправильная причина красного статуса (п. 4).*

## 2. Стратегия проверки по типу задачи

- **feature** — тесты по каждому `REQ-n`: валидные данные, некорректные данные, граничные значения, сценарии ошибок.
- **bugfix** — первый тест воспроизводит баг и падает. Отдельно зафиксируй корневую причину (не симптом) — она попадает в отчёт. Проверь, нет ли той же ошибки в соседнем коде; найденное — в отчёт как наблюдение, без исправления вне рамок задачи.
- **refactor** — сначала характеризационные (golden) тесты, которые фиксируют текущее поведение как есть, включая странное. Странное поведение не исправляй молча: сообщи пользователю. Эти тесты зелёные до рефакторинга и остаются зелёными после. Красного статуса здесь нет — вместо него **контрольная поломка**: временно сломай проверяемое поведение (например, верни другое значение), убедись, что тесты краснеют, и верни код (`git restore -- <файл>`). *Почему: зелёный тест, который не краснеет при поломке, ничего не охраняет.*
- **infra/config** — верификационный сценарий, согласованный в плане: сборка образа, `terraform plan`, `dry-run` миграции, проверка схемы, линт конфигурации CI. Красный статус = сценарий показывает отсутствие нужного результата.
- **ui** — E2E-тест или снапшот; если автоматизация неприменима — согласованный ручной сценарий (шаги и ожидаемый результат) и скриншот как доказательство.
- **perf** — бенчмарк с порогом из спецификации; фиксируй окружение и число прогонов, сравнивай медианы.
- **docs** — сборка документации или проверка ссылок, если они есть в проекте; иначе — вычитка и дифф в отчёте.
- **legacy без тестов** — отдельный шаг: подключить тестовый фреймворк, написать один смоук-тест, добиться зелёного прогона. Затем — по типу задачи.

## 3. Требования к тестам

- Проверяют **поведение через публичный интерфейс**, а не детали реализации — иначе рефакторинг ломает тесты без изменения поведения.
- Каждый `REQ-n` покрыт хотя бы одной проверкой. Ссылку на требование ставь в имени теста или комментарии (`# REQ-3`).
- Внешние зависимости (сеть, время, случайность, файловая система) изолируются фикстурами и моками; тестируемая логика — никогда.
- **Матрица трассировки** ведётся в спецификации: `REQ-n → тесты → статус`. Требование без проверки помечается «непокрыто» и попадает в отчёт.

## 4. Красный статус

1. Запусти тесты шага, сохрани сводку и релевантные строки вывода.
2. Проверь причину:
   - **правильная:** assertion, `NotImplementedError` / not implemented, ожидаемое исключение не выброшено;
   - **неправильная:** синтаксическая ошибка, ошибка импорта, отсутствующая фикстура, сломанное окружение, таймаут.
3. При неправильной причине исправь тесты или окружение и повтори. До заморозки свои новые тесты править можно.

Для refactor вместо красного статуса — контрольная поломка (п. 2); её вывод тоже идёт в отчёт.

## 5. Заморозка

**Что заморожено:** все тесты и снапшоты, существовавшие на момент Baseline, и тесты шага — после заморозки. Добавлять новые тесты можно в любой момент.

**Как заморозить** (способ записан в `.ai/PROJECT.md`):

- **Коммит `test(...)`** — по умолчанию для M/L. Когда красный статус по правильной причине подтверждён, закоммить тесты и каркас отдельным коммитом `test(<область>): … [REQ-…]`. Коммит может быть красным: ветка ещё не опубликована.
- **Контрольные суммы** — если хуки проекта запускают тесты при коммите (красный коммит невозможен, а `--no-verify` запрещён) или коммиты агенту запрещены:

  ```bash
  bash <SKILL>/scripts/freeze.sh record "$MAIN/.ai/tasks/<slug>/freeze-step-N.txt" tests/test_x.py tests/test_y.py
  # перед коммитом реализации — и ревьюер по коммиту:
  bash <SKILL>/scripts/freeze.sh verify "$MAIN/.ai/tasks/<slug>/freeze-step-N.txt" [<коммит>]
  ```

  Тесты тогда коммитятся вместе с реализацией; `verify` доказывает, что они не менялись после заморозки. `record` печатает отпечаток списка — запиши его в журнал и в отчёт о шаге сразу при заморозке; `verify` печатает его снова, и совпадение показывает, что список не подменён. Вывод `verify` — в отчёт о шаге.

  Список перезаписывается только после согласованной правки теста: `freeze.sh record --reason "<что согласовано>" …`. Без `--reason` повторная запись отклоняется, а с ним прежние строки и причина остаются в файле, и `verify` сообщает число перезаморозок.
- **Класс S** — красный вывод показывается в отчёте. Тест в новом файле коммитится вместе с исправлением; тест, дописанный в существующий тестовый файл, — отдельным коммитом `test(...)` сразу после `fix(...)`: оба коммита зелёные и проходят любые хуки проекта (`references/git-safety.md`, «Коммиты»).

`<SKILL>` — папка этого skill, например `~/.claude/skills/dev-workflow`; `$MAIN` — основная рабочая копия (SKILL.md, п. 8).

**После заморозки:**
- **Механическая правка** (импорты, имена и пути после переименования кода; что именно проверяется, не меняется) — мягкий гейт: сообщи, в полуавтономном и автономном режимах продолжай с `[ДОПУЩЕНИЕ]`. Отдельным коммитом `test(...)` с пометкой «механическая правка» в описании. В Claude Code `guard-edit.sh` пропускает в существующих тестах только дописывание: правку строк он отправляет пользователю на подтверждение, а где спросить некого (автономный режим, обход прав), блокирует — тогда это жёсткий гейт, шаг `[!]`.
- **Правка по существу** (проверки, ожидаемые значения, удаление теста) — жёсткий гейт: объясни, чем тест противоречит спецификации, предложи правку, получи согласие, внеси её **отдельным** коммитом `test(...)` с пометкой «согласовано» в описании. Если заморозка контрольными суммами — после правки перезапиши список (`freeze.sh record --reason "<что согласовано>" …`) и отметь это и новый отпечаток в журнале.

*Почему: тест, который можно править вместе с кодом, перестаёт быть независимой проверкой.*

## 6. Реализация

- **Минимальная** — без функциональности сверх требований шага.
- **Общая** — работает для всего класса входов из спецификации, а не для тестовых значений. Самопроверка: «пройдёт ли код, если подставить другие валидные данные?» Возврат константы ради зелёного теста — нарушение инварианта 2.
- Не трогай код вне рамок шага. Замеченное по пути (баги, долг, возможный рефакторинг) записывай в журнал как предложение.

## 7. Ритм прогонов

- После каждого изменения — тесты текущего шага.
- Перед объявлением шага завершённым — полный набор, линтер, типы, сборка (что есть в проекте).
- Сверка с Baseline: новых падений и новых ошибок линтера/типов быть не должно. Улучшения относительно Baseline отмечай отдельно.
- Чего-то в проекте нет — пиши «не применялось», не выдумывай результат.

## 8. Рефакторинг

Только на зелёных тестах, только в рамках затронутого кода, с повторным полным прогоном после.

## 9. Definition of Done шага

Все пункты измеримы и проверяются на последнем коммите шага:
- тесты шага зелёные; полный набор без новых падений относительно Baseline;
- линтер и типы без новых ошибок (если используются);
- сборка или запуск проходит командой из `.ai/PROJECT.md`;
- заморозка цела: тесты шага не менялись после коммита `test(...)` или `freeze.sh verify` → «Заморозка цела»;
- требования шага отмечены в матрице трассировки;
- коммит сделан; статус шага и журнал обновлены; отчёт о шаге выдан (`references/reporting.md`).

## 10. Отладка и эскалация

При падении: прочитай вывод → сформулируй одну гипотезу → проверь минимальным изменением → перезапусти. Записывай гипотезы в журнал, чтобы не повторять их. Неудачную правку своего файла откатывай пофайлово (`git restore -- <файл>`), а не массово.

Стоп-условия и действия — SKILL.md, п. 7. Отчёт — формат «Эскалация» в `references/reporting.md`.
